# Bug Report

## Summary
**Title**: The first mouse motion after the cursor is captured again turns the view by its full travel (no discard, ADR-0014 §3)
**ID**: BUG-0014
**Severity**: S3-Medium
**Priority**: P2-Fix soon
**Status**: Fixed (verified windowed: first motion after recapture 0.0000 rad, next 10 px -0.0250 rad)
**Reported**: 2026-10-15
**Reporter**: godot-specialist, ADR-0014 Verification 4

## Classification
- **Category**: Input / Camera
- **System**: core/controller (`LocalInput`), core/ui (`InputContextStack`)
- **Frequency**: Always (windowed)
- **Regression**: No. `InputContextStack`'s doc comment lists the discard as "Not built yet"

## Environment
- **Build**: `73d873e`
- **Platform**: Windows 11, Godot 4.7.2.stable.official, windowed (headless ignores `Input.mouse_mode`)

## Reproduction Steps
1. Run `tests/integration/ui-input-focus/adr_0014_verification_test.gd` without `--headless`.
2. `test_v4_first_motion_after_recapture_is_discarded` pushes `OVERLAY` (mouse VISIBLE) and pops it (mouse CAPTURED), then injects a 400 px relative motion with `Input.parse_input_event`.

**Expected Result**: ADR-0014 §3: the first relative motion after a switch back to captured, or after focus returns, is discarded; yaw change 0.
**Actual Result**: yaw changes by -1.0000 rad (57°, 400 px x 0.0025 rad/px); the next 10 px motion turns -0.0250 rad as normal. Mouse modes were 2 -> 0 -> 2 as expected.

## Notes
- Whether Windows actually delivers a large first relative motion on recapture is not settled by injection (the engine's own warp-to-centre is OS-side); this test shows only that nothing in our code would discard one. A manual alt-tab / overlay round trip with a real mouse would settle the engine side.
- Fix: `InputContextStack.reapply_mouse_mode()` arms a one-shot discard whenever it writes the captured mode (a switch back to it, or focus-in from the client root); `LocalInput.handle()` drops the next `InputEventMouseMotion` via `take_motion_discard()`. With a stack set, `LocalInput` no longer re-captures on focus-in itself, so the stack stays the sole writer. Regression test: `tests/unit/ui-input-focus/recapture_motion_discard_test.gd` (headless; failed before the fix).
- Original fix direction: on a switch to captured (`InputContextStack._changed` / `reapply_mouse_mode`, and `LocalInput`'s own focus-in recapture) arm a one-shot flag that `LocalInput._input` consumes on the next `InputEventMouseMotion`. The test above is the regression test; it fails today.

## Playtest note (2026-10-15)

- The designer saw no camera jump with a real mouse after closing the wheel or alt-tabbing (main 83b5704, before this fix). The jump was reproduced only with an injected 400 px motion, so Windows on this machine sends no jump on recapture. The discard stays as a guard (ADR-0014 section 3).
