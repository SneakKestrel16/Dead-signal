## Investigation 2026-10-16
- **What the test measures**: wall clock. `Time.get_ticks_usec()` is taken around each server tick of the controller's work (movement, hold checks, ray casts) for 600 ticks after a 60-tick warm-up. It runs up to `PROFILE_ATTEMPTS` (3) profiles and asserts on the **minimum** of their p95s, so the min-of-attempts mitigation already exists. It does not help when the contention lasts longer than one 48 s run.
- **Source of the bound**: `design/gdd/first-person-controller.md` Performance AC (line 367): <= 0.5 ms per tick at p95 over 600 ticks, **on the target server hardware**. The GDD calls it a placeholder; technical-director pins it with the Network Authority ADR's tick rate. The test's `BUDGET_P95_USEC := 500` cites that AC. Not widened.
- **Thread CPU time**: Godot 4.7 exposes no per-thread CPU-time API to GDScript; `docs/engine-reference/godot/` lists only `Time.get_ticks_*` (this is inference from the absence of an API, and the 4.7 `Time`/`OS` class reference would settle it). A CPU-time measure would need a GDExtension or an OS call. That is not a minimal fix, so it was not done.
- **Runs** (`b490e9b`, wt-bugs, the file alone, headless, 5 runs). The machine was **not idle**: 3 other agents' Godot processes were running throughout (`ps -W`), and no idle window was available. Per run, the p95 of attempts 1/2/3 (min p95 in brackets), p50 329-379 us:
  - 645/670/783 (645), FAIL
  - 649/598/582 (582), FAIL
  - 595/577/595 (577), FAIL
  - 522/595/653 (522), FAIL
  - 607/617/591 (591), FAIL
  - Each run: `Statistics: 3 test cases | 0 errors | 1 failures | 0 flaky | 0 skipped | 0 orphans | FAILED` (about 48 s; the two chase cases pass).
- **Honest state**: under parallel-agent load the controller cost is p50 about 340 us and min-p95 522-645 us, so it **fails** the 500 us bound in 5 of 5 runs. The only idle-machine data point on record is the smoke run at `72a2e69` (2026-10-15, no agents running): p95 348 us, PASS. Whether the cost fits the budget on an idle machine is **not re-established** today. A 5x run with no other Godot or agent process running settles it, and the AC itself asks for the target server hardware. p50 sits well under budget while p95 swings by 200+ us with load, which points at contention, not code (inference).
- **Decision needed (lead / technical-director)**: keep an absolute wall-clock gate in the automated suite and only run it on an idle machine; or move it to a manual perf check on target hardware; or measure CPU time through an extension. None of these changes the 500 us figure.

## Decision 2026-10-18 (AD-250)
- **Keep the absolute wall-clock gate, idle machine only.** The 500 us bound is unchanged. The test's doc comment and
  failure message now say a failure with other Godot or agent processes running is not a regression until it
  repeats on an idle machine.
- **Why not the others**: CPU time needs a GDExtension or OS call (see Investigation); a manual-only check drops the
  automated signal that already catches a real regression on an idle run.
- **Idle run at `8d16dfe`** (the file alone, no other Godot process): p50 297 us, p95 368 us, max 677 us, PASS on
  attempt 1. The full suite at `8d16dfe` also passed (1758/1758) with no agents running.
- **Still open**: the AC asks for the target server hardware, which is not chosen yet. Re-measure there when it is.
