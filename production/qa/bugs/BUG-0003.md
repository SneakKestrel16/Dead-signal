## Technical Context
- **Error message**: `Expecting to be less than or equal: 3.016667 but was 4.325000`
- **Likely area**: whether the bound's model of ENet detection is right (the ping interval, and which peer's `set_timeout` applies on the client side). `net_authority.gd:384` sets the timeout on the server's peer of each client; the client's peer of the server needs checking. This is inference: an ENet trace of the failing run would settle it.
- **Workaround**: re-run. Do not widen the bound before the cause is known.

## Evidence
- Full-suite run during CI-4, 2026-10-14: 452 cases, this one failed.
- Isolated runs: PASS, PASS, FAIL (4.325 s).
- 2026-10-15, SD-6 merge full suite with four agents running: `tests/integration/borrowed-face/transforming_visibility_test.gd` (real ENet, 150 ms RTT, 250 ms bound) failed 11 assertions in 12 s; isolated runs PASS, PASS (3.9 s). Same class: a real-ENet timing bound under parallel load. Also reported by the SD-5 agent's targeted run. Bound not widened.

## Fix
- **Root cause**: the same one as BUG-0012. ENet checks a peer's timeout only when a retransmit fires, and the retransmit timeout doubles from rto0 = rtt + 4 * variance. With `enet_timeout_limit` 32 the check lands at the first retransmit past `max`, so detection scales with the client's RTT estimate (about 100 ms under frame jitter). That gives 3.7-4.3 s on the client side against about 1.2 s on the server side.
- **Change**: already in tree from BUG-0012: `data/knobs/net.tres` `enet_timeout_limit` 32 -> 8 and `enet_timeout_min_ms` 1000 -> 750 (max stays 2000). No new code. The bound (`max + ENET_PING_INTERVAL_S + tick` = 3.017 s) is unchanged.
- **Regression test**: the existing `test_killed_server_is_detected_by_the_client_within_the_enet_timeout` with BUG-0012's `_jitter_rtt` (inflated client RTT estimate). It reads the knobs from `data/knobs/net.tres`, so the shipped values are what it tests.
- **Watched fail** (2026-10-16, wt-bugs, headless, alone): an uncommitted copy of the suite with the knobs set in memory to the pre-BUG-0012 values (32, 1000, 2000) failed 3 of 3 runs, with host-left at 4.232, 4.352 and 4.187 s (`Expecting to be less than or equal: 3.016667 but was 4.232000`). That is the 4.325 s this report describes. The copy was deleted afterwards.
- **Runs on current knobs** (`59cbcb8`, alone, headless): 10 of 10 pass, `Statistics: 12 test cases | 0 errors | 0 failures | 0 flaky | 0 skipped | 0 orphans | PASSED` each run. Host-left at 2.363, 2.250, 2.385, 2.284, 2.396, 2.250, 2.215, 2.398, 2.214, 2.254 s (bound 3.017 s). Dead-peer at 1.156-1.228 s. No leaked-at-exit lines.
- **Not covered**: these were idle-machine runs. The 2026-10-15 parallel-load failure of `transforming_visibility_test.gd` (Evidence above) is a different test and is not addressed here.
